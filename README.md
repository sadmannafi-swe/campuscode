# CampusCode

**Learn. Practice. Grow.** — a free, mobile-friendly online IDE, programming course and problem-solving platform for **C** (primary) and **Python** (secondary), in English and Bangladeshi Bangla.

- **IDE first** — write and run C/Python in the browser with custom input, without enrolling in anything. Guests can run code; signing in adds saving, history and progress.
- **Problems** — browse/filter/search, solve in the IDE, *Run* against public samples, *Submit* against hidden tests judged on the server.
- **Community problems** — students author problems; public ones go through moderator review.
- **Courses** — the 32-lesson C curriculum (playlist order) and a 12-lesson Python course, bilingual, stored in Supabase.
- **Progress** — solved counts, streaks and achievements calculated only by trusted database logic.
- **Admin** — a separate, role-protected dashboard for users, problems (incl. hidden tests), lessons, roadmap, reports, announcements and platform switches.

## Supabase setup

1. Create a project at supabase.com.
2. Link and push the schema:
   ```bash
   npx supabase login
   ```
   ```bash
   npx supabase link --project-ref <your-ref>
   ```
   ```bash
   npx supabase db push
   ```
   (Or paste each file in `supabase/migrations/` into the SQL editor, in order.)
3. Load the official content (idempotent — safe to re-run):
   ```bash
   psql "$SUPABASE_DB_URL" -f supabase/seed.sql
   ```
   or paste `supabase/seed.sql` into the SQL editor.
4. **Auth → URL configuration:** set *Site URL* to your deployed URL and add `<site>/**` to *Redirect URLs* (plus `http://localhost:5173/**` for development) — Google sign-in returns to `/login`, password reset to `/reset-password`.
   **Auth → Sign In / Providers → Email:** turn **Confirm email off** — CampusCode signs people in immediately after sign-up (name, email, password, confirm password). If it is left on, the app falls back to a "check your inbox" screen.
   **Google sign-in:** in Google Cloud Console create an OAuth client (type *Web application*) with authorised redirect URI `https://<ref>.supabase.co/auth/v1/callback`, then paste its Client ID and Secret into *Auth → Sign In / Providers → Google* and enable it. Until then the "Continue with Google" button explains that Google sign-in isn't enabled yet.
5. **Storage:** the migration creates `avatars` (public read, users write only inside their own `<uid>/` folder, 2 MB, images only) and `course-assets` (public read, admin write).

### Administrator (one-time bootstrap at `/ccadmingo`)

CampusCode has **exactly one administrator**, fixed by a one-time setup:

1. Open `https://<your-site>/ccadmingo` and choose **Continue with Google**.
2. The first account that completes setup with a **verified Google (Gmail) identity** claims the single admin slot (`claim_initial_admin()`, an atomic insert into the one-row `admin_identity` table). Email/password accounts cannot claim it.
3. From then on `/ccadmingo` shows only an administrator sign-in; any other account — including valid student accounts — is shown *Access denied*. `/admin/*` redirects guests to `/ccadmingo`.

Admin status is computed only by `is_admin()` (= "is this the claimed identity"), never from e-mails or client flags. Roles cannot be granted from the dashboard, scripts or `bootstrap_admin` any more. To hand the role to someone else, the project owner runs in the SQL editor `delete from public.user_roles where role = 'admin'; delete from public.admin_identity;` and the next verified Google account claims it at `/ccadmingo`.

## Judge0 setup

Code never runs in the browser or on the app server. The `execute` and `submit` Edge Functions send it to Judge0's sandbox.

**Default — public instance (works out of the box):** with no `JUDGE0_URL` secret, the functions use Judge0's free public instance `https://ce.judge0.com` (no key). This is what the live site uses today. It is shared with everyone and may be rate-limited or slow at peak times, so it suits a pilot or small classes. For heavier use, switch to option A or B; only the secrets change.

**Option A — RapidAPI (fastest to start):** subscribe to *Judge0 CE* on RapidAPI, then:
```bash
npx supabase secrets set JUDGE0_URL=https://judge0-ce.p.rapidapi.com JUDGE0_API_KEY=<rapidapi-key> IP_HASH_SALT=<random>
```
Free/basic RapidAPI plans have a **small daily request quota**; each *Submit* uses one Judge0 submission per test case plus polling requests. Check the current plan limits and pricing before launch.

**Option B — self-host Judge0 (recommended for real classes):** run Judge0 1.13.x with Docker on a VM (see the Judge0 repository's deployment guide; it requires cgroup support), set `AUTHN_TOKEN` in `judge0.conf`, put it behind HTTPS, and set `JUDGE0_URL` + `JUDGE0_API_KEY=<AUTHN_TOKEN>`. Costs are just the VM.

If `JUDGE0_URL=off`, Run/Submit return a clear *"Code execution is not configured"* message — results are never simulated.

**Built-in limits:** 64 KB source and stdin, 3 s CPU / 128 MB for runs, per-problem limits for judging (500–5000 ms, 16–256 MB), networking disabled, 1 MB file writes, and rate limits — signed-in 15 runs/min & 400/day, guests 5/min & 40/day, submissions 6/min & 150/day. An admin can pause all execution from *Admin → Settings*.

### Deploy the Edge Functions
```bash
npx supabase functions deploy execute --no-verify-jwt
```
```bash
npx supabase functions deploy submit
```
```bash
npx supabase functions deploy certificates --no-verify-jwt
```
`execute` skips gateway JWT verification so guests can run code; it validates the JWT itself when one is present. `certificates` does the same: its `render` action is called by the database, and `sync` / `download` validate the student's JWT themselves.

## Security model (summary)

- **RLS on every table.** Users read/write only their own snippets, progress, submissions, history and notifications.
- **Hidden tests** are readable only by the problem's author and admins; the judge reads them with the service role inside `submit`. Responses never include hidden input/output or program output for a hidden test.
- **Verdicts, stats, streaks, achievements, solved counts and problem counters** are written only by the service role or `SECURITY DEFINER` triggers. Self-authored problems never count toward solved stats.
- **Profiles:** column-level grants block changing `status`; guard triggers stop students from publishing, featuring or marking their own problems official, and keep lesson completion one-way.
- **Admin:** `is_admin()` is evaluated from `auth.uid()`; the UI gate is convenience only. Admins can't demote or suspend themselves.
- **Secrets** live only in Edge Function secrets; the service-role key is used only by `scripts/grant-admin.mjs` on your machine.

## Lesson videos

- The C course uses the playlist [C Programming Bangla Tutorial](https://youtube.com/playlist?list=PLdl6zXgLsy3zwNjSMiYlOZOr20sykTfgo) (33 videos, "Bangla Coding Tutor"). All 33 were inspected (title, duration, description, embed permission): video 1 is the course trailer (course intro); videos 2–33 map one-to-one to lessons 1–32. The mapping lives in `supabase/content/videos.mjs` and is stored in `learning_videos` (YouTube IDs only — never embed HTML). Admins can attach, change or remove a lesson's video in *Admin → Lessons → (lesson) → Lesson video*.
- Videos play inside CampusCode through the official YouTube IFrame Player API (privacy-enhanced `youtube-nocookie.com` host). YouTube's own controls (play/pause, seek, time, volume, fullscreen, ⚙ settings incl. quality) stay intact; CampusCode adds speed chips (only rates the player reports), a caption-language picker (only tracks the player exposes; Bengali preferred), resume, an end-of-video panel and an opt-in "auto-play next lesson".
- Manual quality selection is not offered by CampusCode because YouTube's `setPlaybackQuality` API has had no effect since 2019; students use the player's ⚙ menu. YouTube's mandatory branding (logo, title, "Watch on YouTube") is left untouched as required by YouTube's terms; those links open youtube.com in a new tab.
- `video_progress` stores resume position and watched time per student. The database caps watched time at 2× real time between saves and marks a video watched at 90% — clients can't set completion, and watching never completes the lesson itself.

## Module quizzes & course completion

The C course has one quiz per module (9 × 8 questions: 6 multiple choice + 2 programming problems). Content lives in `supabase/content/c-quizzes.mjs`; `npm run seed:build` **compiles and runs every "what does this print?" question with gcc** and fails if the marked answer is not the real output, and verifies each programming problem's C and Python references on every test.

- **Unlocking:** a module's quiz opens when all its lessons are completed; the next module unlocks only when the previous quiz is passed. Lessons of locked modules can be read but not marked completed (enforced by a database trigger).
- **Attempts:** started, saved and graded only by RPCs (`start_quiz_attempt`, `save_quiz_answer`, `submit_quiz_attempt`). Questions and option order are reshuffled per attempt; answer keys are in `quiz_answer_keys`, unreadable by students. A programming question is correct only if the judge recorded an **accepted** submission *during that attempt* (Solve in IDE → existing problem workspace; hidden tests stay server-side). If code execution is unavailable, the question simply counts as incorrect — nothing passes by default.
- **Rules:** 6/8 (75 %) passes; 3+ incorrect fails; unlimited retakes (whole quiz); failed attempts never reset lesson progress; a passed quiz stays passed. Correct answers and explanations are shown only after submission.
- **Course completion** (`course_completions`): all published lessons + all module quizzes + any configured required practice / final assessment, computed from trusted rows. It is recorded automatically on the event that satisfies the last requirement (lesson completion, judged submission, quiz pass) and then triggers certificate issuance. A course without any server-verified requirement (quizzes or a judged assessment) is never marked complete.
- **Reconciliation:** `pg_cron` runs `reconcile_certificates()` every 5 minutes: it retries pending certificate PDFs and re-checks recent activity for completions whose triggering event failed.

## Certificates of Completion

Every student can earn one **Certificate of Completion per course**. It is issued automatically (no admin approval) when the course is completed. A certificate counts as **issued only once its PDF is stored**: until then it shows as *Preparing* in **Profile → My certificates**, does not verify publicly and sends no notification; the notification is sent exactly once when the PDF lands.

**Requirements** (checked only in the database, from trusted rows — `certificate_eligibility()`):
1. every published lesson of the course is completed (`lesson_progress`; watching a video never completes a lesson),
2. every **required practice** problem is solved (written only by the judge),
3. the **final assessment** score is ≥ the pass mark (70 %, can be raised, never lowered): the weighted share of hidden tests passed by the student's best judged submission on each assessment problem,
4. the course has certificates enabled and is fully configured, the account is active and has a full name.

If a course has no practice or no assessment configured, **nothing is issued** — the admin screen lists exactly what is missing. Both seeded courses start unconfigured on purpose: an admin chooses the practice and final-assessment problems in *Admin → Certificates → Course requirements*, enables the course, and (once) presses *Issue to students who already qualify*.

**Issuance** — `issue_certificate_if_eligible()` runs from triggers on lesson completion and on every judged submission. It is idempotent and race-safe (advisory lock + `unique (user_id, course_id)`), draws a unique `CC-YYYY-XXXXXXXX` number and a 192-bit URL-safe verification token, snapshots the printed name/course, logs `certificate_events`, sends exactly one notification and asks the `certificates` Edge Function (via `pg_net`, after commit) to render the PDF. A render lease prevents duplicate rendering; if rendering fails it is logged and retried on the student's next profile visit or download.

**PDF** — A4 landscape, built on the Canva design itself: `public/certificate/template.pdf` is rendered from the supplied PPTX by `scripts/certificate/build_template.py` (LibreOffice + the design's embedded fonts, used only to render that document and never copied into the repo). The Edge Function overlays the name, course, issue date, certificate ID, verification URL, issuer line and a vector QR code at positions measured from the design (`supabase/functions/certificates/layout.ts`). Long names/titles shrink and wrap to two balanced lines inside the free space; Bangla names are shaped with Noto Sans Bengali. The design's Brick Sans is a commercial Canva font, so dynamic text uses the closest open alternative, Jersey 10 (see `public/certificate/fonts/LICENSES.md`). No signature is ever drawn.

**Storage & privacy** — PDFs live in the private `certificates` bucket (no storage policies for anon/authenticated). Downloads are 5-minute signed URLs issued after an owner/admin check; revoked certificates can't be downloaded by students. `/verify-certificate/:token` is public and calls `verify_certificate()`, which returns only status, printed name, course, certificate ID, issue date and "CampusCode" — never e-mail, user IDs or account data. Verification pages are `noindex`.

**Signature line** — the issuer name *Nafi* is typeset in Great Vibes (OFL) above “Authorized Issuer” (text, not an image).

**Admin** (*Admin → Certificates*, *Admin → Quizzes*) — search by student/username/course/ID, filter by course, status and date, view details with the issuance record, download, copy the verification link, and revoke with a mandatory reason (the student is notified; the public page shows *Revoked*). Revocation is final.

**Configuration** — nothing to set by hand. Optional: `CERT_SITE_URL` Edge Function secret if the site moves off `https://campuscode-cpy.vercel.app` (used for the QR/verification URL and to load the template). The database's callback URL is the `certificates.functions_url` row in `platform_settings`.

## Content

- `supabase/content/*.mjs` is the source for courses, lessons (English + Bangla), problems, topics and achievements.
- `npm run seed:build` compiles and runs every lesson example (gcc / python3) to record its real output, and for every problem runs the Python reference solution on each test input **and** cross-checks the C reference solution — the build fails if they disagree. Current seed: 2 courses, 44 lessons, 44 verified examples, 31 problems, 178 verified tests.
- Seed data contains official content only — no user accounts, credentials or fake statistics.
- Admins can edit all of this later from the admin dashboard.
